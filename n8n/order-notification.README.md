# Заказ → уведомление WhatsApp

[Все сценарии n8n](README.md) · [JSON для импорта](order-notification.json)

## Подготовка

Импортируйте `order-notification.json`. Создайте входящий Header Auth `X-Workflow-Key` и отдельный исходящий Header Auth `Authorization: Bearer YOUR_KEY`. Ключ WAIX должен иметь право `messages:write`. Описание всех узлов: [схема сценария](README.md#что-делает-каждый-узел).

В **Prepare request** задайте `connectionId`, `templateName`, `language`. Пример передаёт одну переменную тела — `order_number`. При другом шаблоне измените `components` под его одобренную структуру.

## Входные данные

Сервер отправляет POST на Test URL или Production URL из вашей установки n8n, с заголовком `X-Workflow-Key` и `Content-Type: application/json`:

```json
{"event_id":"00dcd40d-ec60-4f65-8991-63ca7c775e47","phone":"+77071234567","order_number":"42","whatsapp_consent":true}
```

Создавайте отдельный сохранённый UUID для каждого события заказа: принят, готов, доставляется. Повторное событие должно находить прежний UUID; уведомление не должно создаваться при любом изменении записи.

## Ответ и ошибки

HTTP `202` означает постановку сообщения в очередь. Сохраните `data.id`, а доставку проверяйте по вебхукам или журналу WAIX.

Неверные поля отклоняются до обращения в WAIX. Ошибки `401`/`403` требуют проверки ключа и прав. Для `429` учитывайте `Retry-After`. После таймаута отправки сохраняйте тот же `event_id` и тело запроса; новый UUID может создать повторное сообщение или OTP-запрос.

Проверьте сценарий с тестовыми данными, затем включите его и переведите backend на Production URL. Ключи и URL внутреннего вебхука не должны попадать в браузер или общие логи.
