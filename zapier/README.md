# WAIX + Zapier

[English](README.en.md) · [Все интеграции](../README.md)

Используйте **Webhooks by Zapier → Custom Request**. Это HTTP-интеграция, а не отдельное приложение WAIX в каталоге Zapier. Для Webhooks нужен подходящий тариф Zapier; условия проверьте в [документации платформы](https://help.zapier.com/hc/en-us/articles/8496083355661-How-to-get-started-with-Webhooks-by-Zapier).

## Настройка сообщения

1. Триггер получает событие заказа или формы с вашего сервера. Передайте сохранённый UUID `event_id`, номер в E.164 и переменные шаблона.
2. В фильтре проверьте согласие клиента и обязательные поля. Не отправляйте уведомление при каждом промежуточном изменении одного заказа.
3. Добавьте **Webhooks by Zapier → Custom Request**. Метод — `POST`, URL — `https://waix.kz/api/v1/messages`. `Data Pass-Through: No`, `Unflatten: No`, `Basic Auth` оставьте пустым.
4. Заголовки: `Content-Type: application/json`, `Authorization: Bearer YOUR_WAIX_KEY`, `Idempotency-Key: <event_id>`. Создайте отдельный ключ с правом `messages:write`. Сценарий с действующим ключом не экспортируйте и не публикуйте.
5. Возьмите тело из `requests.json`. Укажите свой Connection ID, одобренный шаблон и язык, сопоставьте телефон и переменные. Формируйте JSON сериализатором — например, `JSON.stringify` в Code by Zapier: так кавычки и переносы строк в пользовательских данных будут экранированы.
6. Сохраните `data.id`. Успех шага означает постановку сообщения в очередь. Проверяйте доставку в журнале WAIX или обрабатывайте вебхуки через сервер с проверкой подписи.

## OTP

Используйте запросы `/otp/send` и `/otp/verify` из `requests.json` и отдельный ключ OTP-проекта. Ваш backend должен связать ID запроса с сессией пользователя и ограничивать попытки. Код, `test_code` и секреты не должны попадать в аналитику и общие логи Zap.

## Доступ и повторная отправка

URL Catch Hook храните на сервере. Если вставить его в форму сайта, любой человек с этим URL сможет запускать сценарий. При потере ответа используйте исходный UUID события и то же тело запроса; не создавайте новый ключ внутри повторяемого шага.

[API WAIX](https://waix.kz/docs/api-reference) · [Поддержка](https://waix.kz/contacts).

## Готовый шаг подготовки запроса

Файл [build-request.js](build-request.js) целиком вставляется в **Code by Zapier → Run JavaScript**. Он проверяет обязательные поля и возвращает безопасно сериализованное тело. В самом Code-шаге ключ WAIX не нужен.

Сопоставьте Input Data:

| Поле | Когда нужно |
| --- | --- |
| `operation` | `message`, `message_status`, `otp_send`, `otp_verify` или `otp_status`. |
| `event_id` | Сохранённый UUID для message / otp_send. |
| `phone` | Строка E.164 для message / otp_send. |
| `whatsapp_consent` | Для message: строка `true` или `1` из подтверждённого согласия. |
| `connection_id` | UUID подключения для message. |
| `template`, `language` | Одобренный шаблон и язык, например `order_ready`, `ru`. |
| `variable` | Одна переменная тела шаблона, до 500 символов. |
| `ttl` | Для otp_send: 60–600 секунд, пустое значение означает 300. |
| `id` | Сохранённый message/challenge ID для чтения статуса или проверки кода. |
| `code` | Для otp_verify: строка из шести цифр, например `012345`. |

Следующий **Custom Request** получает `method`, `url`, `body` из результата Code-шагa. `Idempotency-Key` добавляйте только для message / otp_send, берите `idempotency_key`. Для GET тело и Content-Type не нужны. В Authorization задайте свой ключ; для OTP — ключ проекта.

Сценарий использует фиксированный домен `waix.kz` и только маршруты API v1. URL и произвольные HTTP-заголовки из входящего события не принимаются.

## Хранение операции и повтор Zap

До первого запуска backend сохраняет UUID и **готовые поля сообщения** вместе с событием. Replay должен использовать тот же snapshot; не считывайте изменившееся имя/шаблон/номер заказа заново из CRM. Сохраните `data.id` ответа WAIX в исходной записи. Если ID уже известен, вызывайте `message_status`, а не новую отправку.

Autoreplay Zapier разрешайте только для сценария, в котором неизменность UUID и тела проверена. Повтор с новым ключом может отправить второе сообщение. `409` при прежнем ключе обычно означает, что изменилась отправляемая операция; не обходите ошибку генерацией нового UUID.

При `400/401/403/422` исправьте входные данные или ключ. При `429` учитывайте `Retry-After`; при `5xx` и таймауте сохраняйте прежние данные. Не запускайте бесконечный Replay: после ограниченного числа попыток передайте событие ответственному.

## OTP и история задач

Вычисление/проверку OTP лучше выполнять синхронно на backend через SDK. Zapier подходит, когда ваша схема допускает задержку и вы настроили доступ и хранение данных задач. Если тариф не позволяет исключить OTP из истории, используйте SDK или наши n8n-сценарии с выключенной историей.

Не передавайте `test_code` из sandbox в следующий клиентский шаг или ответ формы. ID challenge хранится в сессии конкретного пользователя. Код с начальным нулём передавайте строкой. Ответ `sent` или `delivered` не подтверждает вход; нужен успешный verify.

## Приёмка

1. Code-шаг возвращает правильный JSON с кириллицей, кавычками и переносами строк.
2. Неверный UUID, телефон и отсутствие согласия останавливают Zap до HTTP.
3. Один event_id при Replay возвращает прежнюю операцию WAIX.
4. После успешной отправки source record содержит ID для дальнейшего status.
5. Неверный ключ вызывает ошибку действия; следующий шаг не помечает операцию доставленной.
6. Доступ к Zap и истории ограничен нужной командой, экспорт не содержит ключей.

JavaScript и тела запросов входят в контрактные тесты репозитория. Сам Zap и ваш тариф проверяются в вашем workspace Zapier; готового приложения Marketplace в этом пакете нет.
