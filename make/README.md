# WAIX + Make

[English](README.en.md) · [Все интеграции](../README.md)

Сценарий использует **HTTP → Make a request** после события формы или заказа. В `requests.json` лежат тела запросов. Это примеры HTTP-интеграции, а не готовый blueprint или отдельное приложение WAIX в Make.

## Настройка сообщения

1. Получите серверное событие с `event_id` (сохранённый UUID), `phone` и переменной `order_number` или `name`. Проверка публичной формы и ограничения частоты остаются на вашем сервере.
2. Добавьте фильтр: у клиента есть согласие на сообщение WhatsApp, номер приведён к E.164, обязательные поля заполнены.
3. Добавьте **HTTP → Make a request**. Метод `POST`, URL `https://waix.kz/api/v1/messages`.
4. Сохраните ключ WAIX в credentials/keychain HTTP-модуля: заголовок `Authorization`, значение `Bearer YOUR_KEY`. Для отправки нужен ключ с правом `messages:write`. Не помещайте действующий ключ в общий blueprint.
5. Добавьте `Idempotency-Key` со значением сохранённого `event_id`. Тип содержимого — JSON. Используйте конструктор структуры данных/JSON: необработанные кавычки и переносы строк из имени клиента не должны ломать запрос.
6. Возьмите тело из `requests.json`, замените Connection ID, имя одобренного шаблона, язык и переменные своими значениями. Включите разбор ответа; переходы по redirect отключите.
7. Сохраните `data.id` вместе с исходным событием. `202` означает постановку в очередь. Доставку проверяйте через подписанный вебхук WAIX или `GET /api/v1/messages/{id}`.

## OTP

Для отправки и проверки кода создайте отдельные сценарии с `POST /api/v1/otp/send` и `POST /api/v1/otp/verify`. Используйте ключ OTP-проекта, сначала в sandbox.

Ваш сервер должен связать ID запроса с сессией пользователя и ограничивать попытки. Не передавайте `test_code` или URL внутреннего сценария в браузер. Выдавайте сессию приложения только после успешной проверки кода.

## Ошибки и повторы

После таймаута сохраняйте прежний UUID и тело запроса. Для `429` учитывайте `Retry-After`; при `400`, `401`, `403` исправьте данные или доступ. Включите режим конфиденциальных данных в настройках сценария и не храните OTP-коды в истории выполнения.

[Документация HTTP-модуля Make](https://apps.make.com/http) · [API WAIX](https://waix.kz/docs/api-reference).

## Полная схема сценария

`Событие → проверка полей/согласия → Data store → HTTP WAIX → сохранить data.id → обновить исходную запись`.

Используйте HTTP **v4**. Создайте API key connection в keychain, место передачи — header, имя — `Authorization`, значение — `Bearer …`. Ключ не должен быть полем входящего webhook. Установите таймаут 30 секунд, выключите Follow redirects, включите разбор ответа. Все адреса WAIX задаются в модуле, а не берутся из события.

### Поля первого запроса

| Источник | Поле WAIX / место |
| --- | --- |
| Сохранённый UUID события | Заголовок `Idempotency-Key`. |
| Настройка сценария | `connection_id`, имя и язык шаблона. |
| Телефон с кодом страны | `to`, например `+77071234567`. |
| Номер заказа / имя | `template.components[0].parameters[0].text`. |
| Подтверждённое согласие | Фильтр до HTTP, не поле API сообщения. |

В Body content type выберите JSON и создайте data structure из `requests.json → message.body`. Подставляйте значения в отдельные поля структуры. Если используете строковый JSON, сначала соберите его через JSON → Create JSON; не склеивайте кавычки вручную.

### Data store перед HTTP

Ключ записи — UUID события, полученный от backend. Поля: `request_json`, `waix_message_id`, `state`, `attempts`, `next_attempt_at`, `request_id`.

Новая операция сначала сохраняет окончательный JSON. Повтор читает эту запись и отправляет её прежний `request_json`. Если `waix_message_id` уже есть, считайте статус, а не создавайте другое сообщение. Уникальность UUID должна обеспечиваться исходной системой. В Make включите последовательную обработку, если сценарий читает и затем меняет одну запись; Data store сам по себе не делает цепочку модулей одной транзакцией.

### Маршруты ошибок

| Ответ HTTP | Маршрут |
| --- | --- |
| 200/202 | Сохранить `data.id` и состояние `accepted`. |
| 400/401/403/404/409/422 | Записать ошибку и request ID, остановить автоматические повторы, передать интегратору. |
| 429 | Сохранить `Retry-After`, запланировать повтор с прежней записью. |
| 5xx / ConnectionError / Timeout | Состояние `retry` с прежним UUID. Не более пяти попыток с увеличением задержки. |

HTTP-модуль обычно направляет 4xx/5xx в error handler. Добавьте обработчик к HTTP, включите incomplete executions, используйте Break для сохранения неуспешного выполнения. Не ставьте Ignore или Resume с фиктивным успешным ответом. Повтор должен продолжать сохранённую операцию, а не пересоздавать UUID в начале сценария.

Долгую задержку храните как `next_attempt_at` и обрабатывайте отдельным расписанием; не держите весь сценарий спящим часами. После пяти неуспешных попыток оставьте запись для ручного разбора. `202` может позже перейти в `failed` — это уже статус сообщения, который нужно получить отдельно.

## Чтение статусов и шаблонов

В `requests.json` есть `message_status`, `otp_status` и `templates`. Это GET-запросы без тела. Подставляйте ID, полученный из WAIX, и ключ с `messages:read`, `otp:read` либо правом чтения шаблонов. OTP send, verify и status используют ключ одного проекта.

При чтении журнала сообщений передавайте **оба** курсора `before` и `before_id` из `pagination`. Не подставляйте URL следующей страницы из непроверенного ответа и не используйте только timestamp.

## Сдача интеграции

Проверьте кавычки/кириллицу в имени, отсутствие согласия, неверный телефон, повтор одного события, неправильный ключ, 429 и обрыв после отправки. В тесте обрыва должно появиться одно сообщение WAIX, а не два. Включите Data is confidential и ограничьте доступ редакторов сценария. Для OTP отдельно проверьте, что история/ответ пользователю не содержит `test_code` и что код с начальным нулём остаётся строкой.

Шаблоны запросов и преобразование данных проверяются локальными контрактными тестами. Сам сценарий собирается в вашем Make: рабочие credentials, mapping источника и настройки error handler нужно проверить в нём перед активацией.
