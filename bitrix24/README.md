# Bitrix24 → WhatsApp: обработчик сделки и очередь

[Все интеграции](../README.md)

`bridge.py` принимает событие **ONCRMDEALADD**, читает сделку и основной контакт через REST Bitrix24, проверяет согласие на WhatsApp и отправляет одобренный шаблон WAIX. Python 3.10+, внешних библиотек нет. Это самостоятельный серверный обработчик, который интегратор устанавливает рядом со своей системой.

Событие записывается в SQLite до ответа Bitrix24. Отдельный worker отправляет сообщения. Повтор события с тем же порталом и ID сделки находит существующую запись. UUID и сформированное тело сохраняются до вызова WAIX; после обрыва соединения используются те же значения.

## 1. Подготовьте WAIX и CRM

- В WAIX подключите номер, создайте ключ с `messages:write` и получите Connection ID.
- Одобрите шаблон с одной текстовой переменной в теле. В этой реализации переменная — **ID сделки**. Например: «Заказ {{1}} принят. Сообщим, когда он будет готов».
- В Bitrix24 создайте входящий вебхук с доступом к CRM для чтения сделки и контакта. Его адрес хранится только в конфигурации сервера.
- Создайте исходящий вебхук события **ONCRMDEALADD** с адресом `https://ваш-сервер/bitrix/deal`. Сохраните application token, member ID и точный домен своего портала.
- Создайте отдельное пользовательское поле контакта типа «Да/Нет» для согласия на WhatsApp. Оно должно заполняться из вашего процесса получения согласия, а не автоматически при установке обработчика.

Сначала используйте тестовую CRM/тестовую сделку и собственный номер с согласием. Запуск worker с рабочими ключами действительно отправляет сообщения.

## 2. Настройте сервер

Скопируйте `bridge.py` в каталог приложения. Задайте переменные из [.env.example](.env.example) через менеджер процессов или защищённый EnvironmentFile. Для рабочего файла: владелец — пользователь сервиса, права `0600`; не храните его в Git.

| Переменная | Откуда взять |
| --- | --- |
| `WAIX_BRIDGE_PORTAL` | Точный домен вашего Bitrix24 без `https://` и `/`. |
| `WAIX_BRIDGE_MEMBER_ID` | `auth.member_id` вашего портала. |
| `WAIX_BRIDGE_APPLICATION_TOKEN` | Секрет исходящего вебхука. |
| `WAIX_BRIDGE_REST_BASE` | HTTPS-адрес входящего вебхука, заканчивается `/rest/ID/SECRET/`. |
| `WAIX_BRIDGE_WAIX_KEY` | Серверный ключ WAIX. |
| `WAIX_BRIDGE_CONNECTION_ID` | UUID подключения WAIX. |
| `WAIX_BRIDGE_TEMPLATE` | Имя одобренного шаблона. |
| `WAIX_BRIDGE_CONSENT_FIELD` | Код поля контакта, например `UF_CRM_WHATSAPP_CONSENT`. |
| `WAIX_BRIDGE_LANGUAGE` | Язык шаблона, по умолчанию `ru`. |

Адрес для REST берётся из конфигурации. Присланные событием URL не используются. Токен, member ID и домен проверяются до записи события; перенаправления HTTP запрещены.

## 3. Запустите два процесса

Оба процесса должны использовать **один абсолютный путь** к базе:

```sh
python3 bridge.py serve --database /var/lib/waix-bridge/outbox.sqlite3 --port 8787
python3 bridge.py work --database /var/lib/waix-bridge/outbox.sqlite3
```

Receiver слушает только `127.0.0.1`. Поставьте перед ним HTTPS reverse proxy, ограничьте размер запроса 32 КиБ и частоту запросов; отключите запись тела и query string в access log. Установите перезапуск обоих процессов через systemd/другой менеджер. Запускайте под отдельным пользователем без root.

SQLite подходит для одного хоста. Каталог состояния — локальный постоянный диск, не NFS и не временный каталог контейнера. Не запускайте несколько копий с разными базами для одного портала: дедупликация действует внутри одной базы. Файл создаётся с правами `0600`. Он содержит телефон и текст шаблона: задайте доступ, резервное копирование, шифрование диска и срок хранения по правилам своей компании.

## 4. Проверьте результат

```sh
python3 bridge.py work --database /var/lib/waix-bridge/outbox.sqlite3 --once
python3 bridge.py status --database /var/lib/waix-bridge/outbox.sqlite3
```

В статусе нет токенов, телефонов и тела сообщения. `accepted` означает, что WAIX принял запрос, а не доставил сообщение. Сохранённый `message_id` можно проверить через SDK `messages.get` с отдельным ключом `messages:read` либо подписанный вебхук WAIX.

| Состояние / ошибка | Действие |
| --- | --- |
| `pending` | Событие принято и ждёт worker. |
| `processing` | Запись взята в работу; lease действует 5 минут. После падения процесса задача снова доступна с прежним UUID. |
| `retry` | Сеть, 429 или 5xx. Отложенный повтор, не больше пяти попыток; учитывается Retry-After в секундах. |
| `blocked` | Нужна проверка интегратора. Самопроизвольных бесконечных повторов нет. |
| `NO_PRIMARY_CONTACT` | У сделки нет основного CONTACT_ID. |
| `NO_WHATSAPP_CONSENT` | В поле согласия контакта нет true / 1 / Y. |
| `CONTACT_PHONE_AMBIGUOUS` | У контакта нет телефона либо несколько разных номеров; выберите получателя в CRM. |
| `UPSTREAM_HTTP_401/403` | Проверьте ключи и права. |
| `RETRY_LIMIT` | Проверьте результат по сохранённому UUID/ID перед ручным продолжением. |

Повторное CRM-событие **не снимает блокировку** и не отправляет сообщение повторно. При разборе спорного результата сохраняйте исходные `id` и `body`; создание новой записи с новым UUID может отправить второе сообщение. Интегратору нужно добавить операторскую процедуру обработки blocked-записей под свой процесс, с аудитом решения.

## Границы готового сценария

Обработчик работает с созданием сделки и основным контактом. Он не подписывается на каждое изменение сделки, не подключает Открытые линии и не создаёт чат операторов. Для другого бизнес-события добавьте отдельное правило и ключ дедупликации. Все номера одного контакта не перебираются автоматически.

Модуль протестирован на локальных ответах REST и WAIX: авторизация, дубли, восстановление lease, обрыв, замороженный запрос, отказ в согласии и предел повторов. Подключение к вашему Bitrix24 проверяется на тестовой сделке после установки; доступ к конкретному порталу в пакет не входит.

```sh
python3 -m unittest discover -s bitrix24/tests
```
